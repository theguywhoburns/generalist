# experiments/ — versioned experiment manifests

## Purpose

Runnable, reviewable provenance for every number reported anywhere in this
repo. Each file here produced a specific result; the `_comment` says which, and
carries the exact command.

These are **not** part of the supported manifest surface — `configs/` is. This
directory is a lab notebook that happens to be executable, so it may carry
cells that are too small, too short, or otherwise unsuitable as defaults.

## Ownership

- `base-492k.json` — shared base for the 492,418-param scaling experiments.
  Every other 492K manifest extends it.
- `arm-ordered.json` / `arm-orderaug.json` — the order-augmentation pair. Read
  them together; neither means anything alone.
- `compute-matched.json` / `compute-matched-wide.json` — the depth-vs-width pair
  at matched parameters **and** matched block-steps. Read together.
- `paramsfree-looping.json` / `paramsfree-wide.json` — the same comparison with
  compute matched and parameters free, holding `d_model`/`n_heads`/`head_dim`/
  `ffn_hidden` identical so only the reuse structure differs.
- `frontier-s01l16.json` … `frontier-s16l01.json` — five points at matched
  parameters and matched compute, sweeping the stages↔width split end to end.
  Generated by `.runs/gen_frontier.py`; solve new points with
  `param_match -- <loops> <stages> <target>`. The first pass was confounded with
  effective batch (see contract 4) and is superseded; the rerun pins
  `auto_batch: false, batch_size: 6`.
- `arch-dyck1-looping.json` / `arch-dyck1-wide.json` — the compute-matched pair
  re-run on `dyck1`, the first architecture comparison on a rung whose answer
  requires dependent multi-step computation. Read the unary-output instrument
  warning in the `_comment` before interpreting.

## Local Contracts

1. **A manifest here must reproduce the run it documents.** When porting a
   manifest from scratch space, verify it rather than eyeballing it:
   ```bash
   cargo run --example verify_port -- research/experiments/X.json /tmp/opencode/X.json
   ```
   `verify_port` compares the fully resolved configs field by field and exits
   non-zero on any divergence. It has already caught four real ones, including a
   depth axis that had silently switched to auto-batch.
2. **Record the settings that actually ran, not the tidy ones.** The depth axis
   runs at fixed batch because that is what was measured; the data axes run
   with auto-batch because that is what produced the reported table. A manifest
   "cleaned up" to a uniform batch no longer reproduces its result.
3. **Put the run command in the `_comment`,** multi-line, with the axis and
   seeds. Someone reproducing this should not have to reconstruct the
   invocation from the manifest.
4. **Note what is deliberately off** and why — `auto_batch: false` on the depth
   axis, `shuffle_eval: false` on the weights-only rung. A knob that looks
   misconfigured invites a well-meaning fix that breaks provenance.
   **`auto_batch: false` is mandatory on any sweep that varies model shape**, not
   a preference: the tuner budgets from measured activation memory, so different
   `d_model` means different realized batch. The frontier manifests shipped
   without it and picked up batches of 64 / 128 / 128 / 128–256 / 256 against a
   requested 6. See `research/AGENTS.md` contract 10.
5. **Checkpoints go under `$repo_root/research/runs/checkpoints-*`.** Not
   `$curdir` and not a bare relative path: the root must stay readable, and a
   bare path resolves against wherever the runner was invoked.
6. **Use `$` path variables, never absolute paths.** `$curdir`,
   `$parent_dir`, `$repo_root`, `$experiment_dir`, `$configs_dir`. An absolute
   path in a committed manifest breaks for everyone else; an unknown variable
   is rejected by the loader, so a typo fails loudly instead of silently
   pointing at the wrong file.
7. **An absent or empty `tasks` key means all eight builtin rungs, not none.**
   `harness/experiment.rs` resolves an empty list to the whole registry, so a
   manifest that inherits from a base with no `tasks` is a *mixture of every
   rung*, not a single-rung run. This is silent — it produces a plausible pooled
   number. Corollary for reading manifests back: `jq '.experiment.tasks'`
   returns `null` for a manifest that legitimately inherits its `experiment`
   block, because `jq` does not resolve `extends`. Never conclude a manifest's
   rung from `jq`; run `cargo run --example run -- <manifest>` and read the
   resolved pool count. Every arm of every architecture experiment in this repo
   resolves to `pool instances: 320` = `per_cell 160 × 2 tracks`, i.e. all of
   them are `subst-fst-fixed` and nothing else.
8. **`extends` resolves relative to the extending manifest's own directory,**
   not the invocation directory. A scratch manifest written outside this
   directory — `.runs/probe.json`, say — must reach back with
   `"extends": "../research/experiments/base-492k.json"` or it dies on
   `No such file or directory` naming the *base*, not the probe. Confusing
   enough that it is worth stating: the error names a file you did not write.

## Work Guidance

Adding a new experiment:

1. Extend `base-492k.json` (or an arm file) rather than copying a config whole.
   Arrays replace rather than union on merge, so `k_set: [0]` is expressible —
   keep that property.
2. Override only what the axis varies; leave the rest inherited.
3. Preflight with `cargo run --example run -- <manifest>`. It resolves
   `extends`, expands `$` variables, validates, and prints cell counts.
4. Run the axis. For two-arm interventions use `examples/arm_compare.rs`, which
   refuses arms that differ by more than the intervention.
5. Read results from `run.jsonl`, not stdout.
6. Record the result in `research/findings.md`, and add a line to the index
   below if the manifest is worth keeping long-term.

## Verification

- [ ] run command present in `_comment`
- [ ] deliberate deviations from the base documented
